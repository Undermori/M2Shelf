# M²Shelf 运行机制说明

M²Shelf 会为你的媒体目录建立一份本地目录册，再结合目录结构、文件名和 Bangumi 信息，把资源整理成便于浏览的作品卡片。播放时，它仍然打开原来位置上的视频。

这份说明面向没有很多代码基础的使用者。你可以从头了解整个流程，也可以直接阅读分类、多碟、同步或常见问题部分。文中的作品名、文件名和目录都是虚构示例。

**适用范围：本次 PR 的源码及 2026-10-06 更新的本地构建。** 版本号保留 0.5.11，包含本文所述的新规则；公开 Release 中同版本的旧构建可能仍有不同表现。

## 先了解几个词

| 名称 | 在软件里是什么意思 |
| --- | --- |
| 资源库 | 你添加给软件扫描的一个目录，例如某块硬盘上的动画收藏目录。可以添加多个。 |
| 扫描 | 查看目录和文件，把位置、名称、大小、修改时间等记入软件自己的目录册。 |
| 索引 | 扫描得到的本地目录册，保存在软件数据库中。浏览页面主要读取它。 |
| 分类 | 判断一个目录是作品、系列、其他资源，还是被你隐藏的条目。 |
| 归属 | 判断某个子目录及其视频属于哪一部作品，例如 CD1 属于外层作品。 |
| Bangumi 绑定 | 在一个本地来源和一个官方作品条目之间建立对应关系。 |
| 来源 | 一部作品在本地的一份资源，可以是一个作品目录，也可以是一个视频文件。 |
| 聚合 | 把多个符合条件的来源放到同一张作品卡片中展示。 |
| 缓存 | 软件保存的封面等副本，用来减少重复下载和读取。 |

分类回答“这个目录怎样组织内容”，Bangumi 匹配回答“这份内容对应哪部作品”，聚合回答“哪些来源可以放到同一张卡片里”。它们会互相影响，但各自解决的问题不同。

## 一 文件和软件记录分别放在哪里

可以把软件的工作分成三处存放的数据和一个展示结果。

| 部分 | 保存的东西 | 哪些操作会影响它 |
| --- | --- | --- |
| 你的媒体目录 | 视频、字幕、音乐、图片、蓝光目录等原始资源 | M²Shelf 读取它；扫描、分类和绑定不会改写这些文件。 |
| 软件自己的数据库 | 文件位置、分类、显示名、Bangumi 绑定、标签、收藏、观看时间和设置 | 扫描及你在软件内的整理操作。 |
| 软件自己的缓存目录 | 下载的封面、复制进来的手工封面 | 获取、更换或清理封面。 |
| 页面上的作品卡片 | 根据索引和绑定临时计算出的浏览结果 | 分类、归属和绑定改变后，卡片会重新计算。 |

例如，你把一个目录的显示名改成“星海旅人 第二季”，软件会在数据库里记住这个名字，硬盘上的目录名仍然保留。给作品加“已看”标签、加入收藏夹，也只改变软件自己的记录。

作品库没有另外建立一套需要你维护的“作品文件”。同一份索引既能按真实目录浏览，也能计算出作品卡片。这样切换视图时，视频位置、标签和收藏不会因为展示方式改变而被搬到别处。

## 二 启动软件时会发生什么

已有资源库时，大致按下面的流程运行：

1. 打开本地数据库，检查是否需要升级数据库结构，读取设置。
2. 恢复窗口尺寸、语言、主题等界面偏好，读取已有索引并显示页面。
3. 如果开启了“启动时自动更新资源库”，在初始化就绪后进行一次后台检查。
4. 启动扫描结束或无需扫描时，尝试补全尚未完成的 Bangumi 官方别称。
5. 如果开启了软件更新检查，查询是否有新的软件版本；下载和安装仍需要你主动操作。

后台任务启动有先后条件，避免重复发起同一种任务。界面也会核对异步结果是否仍然适用于当前页面，例如你已经切换资源库时，不会让旧页面的迟到结果把新页面覆盖掉。

第一次使用时，需要先添加资源目录并选择识别方式。首次引导添加资源库后会启动扫描，已有数据的后续浏览则主要依靠数据库。

### 启动扫描的默认值

| 数据库情况 | 没有另外修改设置时的行为 |
| --- | --- |
| 新建数据库 | 启动自动更新默认开启。 |
| 已有数据库，过去没有保存过这项设置 | 升级后默认关闭。 |
| 已有数据库，明确保存过开启或关闭 | 保留原来的选择。 |

旧库默认关闭，是为了让你自行决定何时进行可能较大的目录读取。开启后的首次更新会实际更新索引，再建立比较基准；它可能需要完整枚举资源库。

这里的自动更新是**每次启动尝试一次**。当前程序没有持续监控硬盘上每一次文件变化的机制。软件运行期间放入新视频后，可以手动扫描；也可以在下次启动且自动更新开启时发现它。

## 三 扫描怎样找到视频

扫描会从资源库目录向下查看各层子目录，记录文件位置、名称、扩展名、大小和修改时间。它根据设置中的扩展名列表判断哪些文件作为视频索引。

默认视频扩展名包括 MKV、MP4、M4V、AVI、MOV、WEBM、TS 和 M2TS。你可以在设置中调整列表。识别扩展名只是判断“这是一份要索引的视频文件”，还没有决定它对应哪部动画。

字幕、图片、音频、文档、压缩包等会作为附件或其他资源记录。它们可以在目录里查看和打开，但不会仅凭自己的存在生成一部作品或参加作品名称的自动搜索。

**普通扫描主要读取文件信息，不分析视频画面、对白或片头来认出动画。** 所以名字和目录组织提供的线索很重要。

### 两种识别方式

添加资源库时要选择“按文件夹识别”或“按视频文件识别”。这个选择影响索引怎样组织内容。

| 识别方式 | 怎样建立来源 | 适合的目录情况 |
| --- | --- | --- |
| 按文件夹识别 | 保留真实目录层级，综合视频分布判断哪个目录承载作品。 | 每部作品有自己的目录，里面放正片、特典和附件。 |
| 按视频文件识别 | 普通视频分别建立为独立来源；作品库还能按证据聚合它们。 | 同一个目录混放多个作品，或者希望每个视频都能独立绑定。 |

按文件夹识别的例子：

```text
动画收藏/
└─ 星海旅人/
   ├─ 01.mkv
   ├─ 02.mkv
   ├─ SPs/
   │  └─ PV.mkv
   └─ Scans/
      └─ cover.jpg
```

软件通常会把“星海旅人”作为作品来源，两个正片和所属特典都归这部作品。Scans 保留为附件目录。

按视频文件识别的例子：

```text
混合视频/
├─ 星海旅人 - 01.mkv
├─ 星海旅人 - 02.mkv
└─ 月影故事 - 01.mkv
```

索引里有三个独立视频来源。在作品库中，前两个有相同作品标题和明确集号线索，可以聚合成一张“星海旅人”卡片；“月影故事”仍然独立。切到按文件夹展示或来源编辑时，仍能操作原始来源。

**已有资源库的识别方式目前不能直接切换。** 两种方式建立来源的单位不同，直接切换可能改变原有记录的身份。添加资源库时应按实际目录组织选择。

### 蓝光目录的特殊处理

BDMV 是蓝光资源常见的目录结构，里面可能有 STREAM 等技术目录和大量编号片段。软件会识别常见结构，把一套蓝光资源作为一个作品单位处理，避免把技术目录或每个流文件都包装成一张作品卡片。

在按视频文件识别模式下，BDMV 仍保留这项特殊规则。`00001.m2ts` 这样的纯编号流文件，也不会被当成“另一部不同作品”的标题证据来拆散多碟资源。

## 四 作品 系列和其他资源怎样判断

在文件夹模式中，软件先看两个问题：当前目录有没有直属视频，下面是否还有含视频的目录分支。这里的“直属”就是视频直接放在这个目录里，中间没有其他子目录。

| 目录情况 | 通常的自动分类 | 含义 |
| --- | --- | --- |
| 有直属视频，没有普通独立媒体子分支 | 作品 | 这个目录本身承载一部作品。 |
| 有直属正片，子媒体分支都是已识别的特典等补充目录 | 作品 | 正片和补充内容共同属于这部作品。 |
| 没有直属视频，下面主要放若干作品目录 | 系列 | 这个目录用于组织和进入下级资源。 |
| 有直属视频，同时还有普通媒体子分支 | 其他资源 | 结构混合，自动判断不直接把整层当成一部作品。 |
| 没有视频，只有图片、音乐等附件 | 保留为资源目录 | 不进入作品库，也不自动匹配作品。 |
| 符合后文的明确多碟规则 | 外层作品 | 即使正片都放在 CD1/CD2 等子目录，外层也可承载作品。 |

例如：

```text
系列收藏/
├─ 星海旅人 第一季/
│  └─ 01.mkv
└─ 星海旅人 第二季/
   └─ 01.mkv
```

“系列收藏”负责组织目录；第一季和第二季各自是作品。“系列”这个标签描述本地组织关系，不等于软件已经确认这些内容在剧情上属于同一个系列。

另一种结构：

```text
混合收藏/
├─ 一段视频.mkv
└─ 另一部作品/
   └─ 01.mkv
```

外层有直属视频，但还有普通媒体子目录，通常归为“其他资源”。**当前作品库不会因为外层有一段视频就把它强行包装成作品。** 下层符合条件的作品仍可以进入作品库。

### 人工分类的优先级

你可以手动设为作品、系列、其他资源或忽略，也可以恢复自动判断。手动选择会保存在数据库里，正常重扫不会覆盖它。

“恢复自动判断”会重新根据当前可用的索引和结构线索分类，并重新计算内容归属。它不会把显示名、标签、收藏和 Bangumi 绑定一并清空。

被单独人工分类的子目录会形成边界。比如你明确把一个 OVA 目录设成独立作品，父作品详情就不会继续把该 OVA 内部的视频平铺进来。

作品库和普通自动匹配共用同一套逻辑作品范围：**有所属视频的作品才进入作品库和自动搜索。** 系列与其他资源不参加普通自动搜索。系列仍可以手动绑定，已有绑定也会保留。

## 五 多碟和补充内容怎样归属

### 明确分卷可以归到外层作品

```text
星海旅人/
├─ CD1/
│  └─ 01.mkv
├─ CD2/
│  └─ 02.mkv
├─ SPs/
│  └─ PV.mkv
├─ CDs/
│  └─ soundtrack.flac
└─ Scans/
   └─ booklet.jpg
```

符合条件时，“星海旅人”会成为一部作品，CD1 和 CD2 是它的分卷。它们的原始目录和文件记录都保留，但不会再各自进入作品库或独立自动搜索 Bangumi。

这里的 `CD1` 和 `CDs` 含义不同。`CD1` 是明确编号的分卷名；`CDs` 里如果只有音乐文件，就属于附件目录。

自动合并需要同时满足几类条件：

1. **分卷名称明确。** 支持 CD1、CD 01、Disc 1、Disk 1、BD1、DVD1、Vol.1、Volume 1 等完整编号形式。目录名只是包含“CD1”几个字，不足以成立。
2. **外层有可用的作品名。** 软件要能从外层名称得到作品线索。
3. **媒体分支结构一致。** 外层的含视频分支要能解释为分卷或补充内容；出现普通独立作品分支时，不自动把它们全部并在一起。
4. **没有明确冲突。** 有意义的视频标题、季度、年份和已有绑定不能明确指向不同作品。
5. **尊重人工边界。** 已手动设成独立作品、系列或其他资源的子目录，会阻止自动把该分支吞进外层。

### 目录叫 Disc1 也可能需要独立保留

```text
星海旅人/
├─ Disc1/
│  └─ 星海旅人 S01E01.mkv
└─ Disc2/
   └─ 星海旅人 S02E01.mkv
```

这里有明确的第一季和第二季冲突，软件不会仅凭 Disc1/Disc2 名称把两季自动合成一个外层作品。不同作品标题、不同官方绑定也会产生类似边界。

如果父目录尚未绑定，而某个分卷已经单独绑定，软件也会保守地把这份明确身份保留下来。只有父子已有身份相容、其他条件也成立时，才可能归到同一作品。

### 补充目录需要主体证据

SPs、OVA、Extras、PV、NCOP、NCED 和部分中文特典名称可作为补充内容线索。正片直接放在父目录时，这些目录通常不会把父作品拆散。

但是，“一个目录下面只有 SPs 或 OVA”不足以自动把外层提升成作品。补充内容的名字本身也不足以证明它是哪部作品；你可以通过人工分类或单独绑定明确它的身份。

这些多碟归属规则用于文件夹识别模式。视频文件识别模式保留逐视频来源和原有 BDMV 处理方式。

## 六 软件怎样识别动画名称并匹配 Bangumi

本地结构确定作品范围后，软件才会为合格来源收集名称线索，并尝试寻找 Bangumi 对应条目。

### 从名字中提取线索

软件会结合显示名、真实目录名或文件名、所属视频的文件名，以及有用的父目录信息。自定义显示名没有抹掉真实名称：原名仍能作为另一条匹配线索。

例如这个名称：

```text
[字幕组] 星海旅人 S02E03 (2021) [1080p][x265][FLAC].mkv
```

软件会尝试区分作品标题、第二季、集号、年份，以及字幕组、分辨率、编码和音轨等技术描述。用于搜索的名字会尽量保留作品身份线索，减少技术文字干扰。

一些处理原则：

- “动画”“Movies”等过于宽泛的目录名不占用搜索关键词名额。
- 名称中同时有中文和其他语言标题时，可以保留多个候选线索。
- 季度和 TV、剧场版、OVA 等形式有助于区分同名条目。
- 分辨率里的数字不能当成年份；像标题本身带数字的电影名也要尽量保留。
- 目录里明确写出的年份比从文件名推断的年份更强。信息模糊或存在多个年份时，会采取更保守的判断。

这些规则有助于提高准确性，但仍可能受错误命名、非官方译名和缺少线索影响。

匹配时，软件会把用于搜索的标题关键词发送给 Bangumi，并请求官方条目详情和封面；视频文件本身不会随匹配上传。关闭 Bangumi 功能后停止新的相关请求，已有绑定和本地缓存仍会保留。

### 搜索候选并比较

单个来源最多使用三个官方搜索关键词。软件把不同查询返回的候选合在一起，比较标题相似度、各语言标题、季度、年份、作品形式和提供方排序等线索。必要时再读取候选的官方详情。

当前默认的直接绑定门槛是 60 分，更高的 82 分用于决定高置信结果的详情补全路径。**这个分数是规则评分，不代表“识别正确的概率”。** 达到门槛也不能绕过明确的季、年份、形式或条目类型冲突。

主关键词的第一个合格官方结果，在本地名称线索足够明确时可以得到额外信任，提升到直接门槛；硬冲突检查仍然生效。同分时会使用提供方排名稳定决定顺序。

当前支持自动绑定 Bangumi 的动画和真人影视条目；书籍、音乐、游戏条目不在这条自动匹配路径中。目录中的原声带和扫描图也不会作为独立作品去搜索。

### 怎样决定写入结果

最高候选达到直接门槛且没有强冲突时，软件保存绑定。线索不足或有强冲突时，保留为未匹配，供你手动纠正。当前没有等待你批准的“待确认”中间档位。

普通扫描和普通匹配会保护已有绑定，不用新搜索结果随意替换它。只有你明确执行重新匹配或手动改绑时，才允许改变原来的对应关系。

“仅匹配现有资源”读取已经建立的索引，不重新扫描硬盘。因此，如果你刚新增了视频，应先扫描，让视频进入索引后再匹配。

### 手动纠正怎样帮助后续识别

手动选择官方条目时，软件会把当前来源的一些有效本地标题记成“人工确认别名”。以后遇到相同本地译名，可以把你确认过的官方条目作为重要线索。

例如，你曾把本地“星海的旅行者”手动绑定到官方“星海旅人”，后续另一份资源使用前一个译名时，就可能受益于这项记录。

这种记录仍受季度、年份和形式等冲突检查限制。如果同一个别名曾被你绑定到不同作品，软件会认为它有歧义，回到普通搜索流程。自动匹配本身不会再把猜测结果学习成人工确认别名。

这份对应关系保存在本地；相关来源的绑定被清除、替换或来源被删除时，对应的学习记录也会清理。

## 七 多份资源为什么会变成一张作品卡片

“全部资源”默认保留原目录卡片。在“设置 → 浏览与扫描”打开“全部资源穿透显示”后，跨目录展示逻辑作品，并根据身份线索聚合来源；关闭后恢复原目录卡片。选择立即生效、自动保存，重启后仍保留。它只控制全部资源页面，不改变扫描方式、分类、详情或实际目录结构。

### 已绑定来源优先看官方身份

```text
资源库甲/星海旅人 BDRip/
资源库乙/星海旅人 WEB/
```

两个来源绑定到同一个 Bangumi 条目时，可以展示成一张作品卡片。展开详情底部的“资源来源”，仍能分别找到它们。

这里比较的是官方条目的身份，而不只是名字是否相同。不同季度绑定不同官方条目时会分开；如果你手动把两季绑定到了同一个条目，作品库也会按你保存的共同身份聚合，所以应先纠正绑定。

### 未绑定来源采用更保守的方式

- 视频文件来源可以在同一个物理目录内，按清洗后的标题、季度、年份和形式分组。
- 文件夹来源不会仅凭同名跨目录自动合并；给它们绑定同一个官方条目后，才有明确的共同身份。
- 证据不足时独立保留，避免把续作或不同季混在一起。

聚合只是页面上的组合，不会合并原始文件记录、改名或移动视频。分类和绑定变化后，页面重新计算分组，所以作品卡片数量可能增加或减少。

### 哪些操作整组执行

| 在聚合作品上操作 | 实际作用范围 |
| --- | --- |
| 绑定、改绑、清除 Bangumi 绑定 | 当前整组来源。 |
| 重试 Bangumi 自动封面 | 整组检查，只处理需要恢复的自动封面来源。 |
| 改名、分类、隐藏、标签、收藏 | 需要选择明确来源，或在展开来源的编辑模式中操作。 |
| 打开某个视频或定位它 | 该视频原始记录对应的文件。 |

整组绑定会把所有来源的修改作为一次完整操作保存。网络请求期间，如果来源被删除、改绑或改变了分组，软件会拒绝过期结果并刷新，避免把旧操作写进新的一组资源。

整组清除绑定后，还会按剩余本地证据重新分组。同目录、标题和季数仍一致的视频可能继续聚合；失去共同官方身份的多个文件夹来源则可能重新分开。

## 八 详情页怎样展示正片 特典和附件

普通作品详情和聚合作品详情使用同一套内容归属规则。

1. 上方视频区保留来源里的直属视频。
2. “作品中的其他资源”先列出所属子目录中的视频，递归展开，平级显示。
3. 视频之后保留附件和原目录入口；已经展开的目录会注明视频已在上方展示。
4. 聚合作品最底部还有可展开的来源列表。

因此，正片放在外层、PV 放在 `SPs/PV/` 时，打开作品后就能在其他资源区直接播放 PV，不必先进入两层目录。CD1/CD2 里的分卷视频也可以在那里直接看到。

递归展示会在独立子作品或人工边界处停止，独立条目仍保留可进入的入口。隐藏目录及其内部内容不会显示。附件没有全部递归搬到最外层，你仍可通过原目录入口查看深层附件。

### 同名视频怎样区分

```text
星海旅人/CD1/01.mkv
星海旅人/SPs/01.mkv
```

文件名虽然一样，视频行会标出相对目录；多来源时还会增加来源标识。播放和定位使用原始文件编号及完整路径，不靠显示出来的“01.mkv”猜文件位置。

子目录视频默认先按相对目录、再按文件名自然排序。自然排序会让第 2 项排在第 10 项之前。去重依据原始文件记录的编号：同一文件不会因为展开过程重复列出，两个不同路径的同名文件仍然各自保留。

打开详情主要读取 SQLite 本地索引，不在这一刻重新遍历整块媒体盘。硬盘暂时离线时，已有名称、绑定和目录记录仍可浏览；播放时则需要原文件能被访问。

### 卡片统计怎样计算

作品的视频数、最近观看时间和最后更新时间按所属内容计算，独立子作品不会重复算进父作品。聚合作品再汇总各来源。

如果两份不同路径的资源都包含同一集，它们仍然是两个视频文件，会分别计数。软件的去重是在避免同一文件被重复展开，没有根据内容指纹把不同文件自动视为同一个。

“作品中的其他资源”区域显示的项目数可能包含视频、目录入口和附件，因此它与视频总数不是同一项统计。

## 九 更新资源库和同步信息怎样运行

在作品上执行绑定时，软件先记住这组来源和它们的分组依据，保存时再核对。如果这期间你只是播放了视频或改了标签，绑定仍可继续；如果来源被删除、被拆成独立作品、改绑，或手工封面发生变化，软件会刷新并提示原操作已经过期。绑定和封面下载分两步进行：封面下载失败时，有效绑定仍会保留。

聚合作品可以包含超过 500 个来源；软件仍然核对完整范围并一次提交。普通编辑模式的批量修改继续保留每次 500 项的上限。封面虽然有文件，也可能损坏；封面重试会检查缓存，并能恢复界面无法解码的自动封面。手工设置的封面不会被该重试覆盖。

软件里有几种不同的更新动作，先按对象区分会比较清楚。

| 更新动作 | 更新什么 | 是否读取媒体目录 | 是否需要网络 |
| --- | --- | --- | --- |
| 手动扫描、启动资源库更新 | 本地文件索引、分类和归属 | 需要枚举目录和文件信息 | 扫描本身不需要；启用 Bangumi 后的匹配阶段需要。 |
| 匹配现有资源 | 尚未绑定或明确要求重匹配的作品对应关系 | 不重新遍历目录 | 需要 Bangumi 网络。 |
| 历史别称补全 | 已有绑定的官方别称 | 不扫描媒体盘 | 需要 Bangumi 网络。 |
| 封面重试 | 某个已绑定作品的自动封面 | 不重新扫描媒体目录 | 下载自动封面时需要。 |
| 软件版本更新 | M²Shelf 程序本身 | 不整理媒体目录 | 需要查询和下载安装包。 |

### 启动增量检查

软件保存一份上次成功观察到的目录信息，称为比较基准。下一次启动检查时，再枚举目录项，比较名称、类型、大小和修改时间。

这份基准可以理解成上一次成功盘点的账本。软件用它找出新增、删除或变化的分支，尽量复用未变化的索引，减少重复分类和自动匹配。

“增量”仍然需要查看目录项来发现深层变化，尤其是软件关闭期间新增的集数。它并不是只看最外层目录时间，也不意味着完全不读盘；节省的是未变化内容的重复索引和匹配工作。

第一次没有基准、有关设置改变、隐藏状态改变，或手动扫描使旧基准失效后，后续检查可能需要重新建立基准。新的基准会在索引成功更新后保存。

没有内容变化的后台检查只更新扫描健康记录，保留当前列表和滚动位置。有变化时才重新读取页面内容，并尽量保留导航状态。

### 多个资源库分别结算

假设本机目录扫描成功，而移动硬盘离线：本机目录可以更新自己的索引和基准；移动硬盘保留旧记录，显示失败状态，之后再重试。

| 状态 | 表示什么 |
| --- | --- |
| 成功 | 该库本轮完整检查或扫描成功，更新最后成功时间。 |
| 部分失败 | 该库有部分内容未能读取，已有未读索引受到保护。 |
| 失败 | 该库无法完成检查，例如整个目录不可访问。 |
| 已取消 | 本轮未完成，不能把未观察到的内容当成不存在。 |

资源库管理会显示最后自动尝试、最后完整成功、结果和错误摘要，失败库在侧栏也有轻量提示。可以在设置里查看情况并手动重试。

完整成功观察后，已经不存在的文件可以从索引中清理；深层读取失败、离线或取消时，不会把未成功观察的旧内容当成删除，失败库也不会推进为新的成功基准。

手动扫描可能已经更新了部分可读内容，取消不会把这些更新全部撤回；保护规则针对的是避免误删未读内容和误记成功基准。此前已经完整成功的其他资源库仍可以单独结算。

### 官方别称的后台补全

官方别称让本地搜索也能找到另一种译名。例如绑定标题显示“星海旅人”，官方别称中有另一译名，输入那个译名仍可搜索到这份资源。

已有绑定的历史补全在启动任务空闲后尝试一次，每次应用运行最多尝试 **32 个不同的官方条目**。同一作品有多个来源，也按官方身份去重；刷新列表和重复调用不会重置预算，失败也会消耗一次名额。

软件保存处理位置，下次启动从后续未完成条目轮换继续，避免前几个失效条目长期挡住后面的内容。成功得到“没有别称”也算完成，不会每次启动都重新请求它。

单个失效条目可以跳过，提供方整体故障会停止本轮。关闭 Bangumi 功能后停止发起新请求。别称补全只更新仍绑定到同一官方条目的别称，不改变绑定、不顺带下载封面，也不生成“人工确认别名”。

### 网络工作有各自的预算

| 任务 | 当前上限 | 你可能看到的结果 |
| --- | --- | --- |
| 单个来源的自动搜索 | 最多三个关键词 | 软件不会无限变换名字查询。 |
| 普通候选的详情补全 | 每个来源最多五个主要候选；高置信路径重点补全胜出项 | 详情信息用于最终比较和保存别称。 |
| 一轮自动匹配的新增详情请求 | 最多 256 次；同一条目复用缓存 | 达到上限后继续依据已有搜索信息判断。 |
| 一次应用运行的历史别称补全 | 最多 32 个不同条目 | 大量旧绑定可能需要多次启动才能补完。 |

32 的限制专门针对历史别称补全，与正常匹配的 256 次详情预算分别计算。网络请求还有原来的有限重试，所以“32 个不同条目”不等于总共只会发出 32 次网络请求。

当前同步以本地索引和官方作品信息为主，没有账号云同步，也不会把你在软件里的收藏或观看记录同步到 Bangumi 账号。

## 十 封面 标签 收藏和观看记录怎样保存

### 封面与绑定分别保存

绑定保存的是“这个来源对应哪个官方作品”，封面是那部作品的一张图片。封面下载失败时，正确绑定仍然保留，页面会提示获取失败，并提供重试。

整组绑定只复用一次官方详情和封面下载，再为各来源保存各自状态。手工封面受到保护；重试只处理没有缓存文件或已经记录获取错误的自动封面来源，已有有效缓存的来源无需跟着重做。

下载的封面和手工选择的图片副本写入软件缓存，不放进你的动画目录。缓存副本有文件大小、格式和图片尺寸检查，先写入临时位置，通过校验后再提交；手工更换图片时，不会先删除原有效封面。

更换缓存目录不会自动搬走或删除旧缓存，旧记录仍可引用原来的封面位置。清理缓存保留作品绑定，但相关封面可能需要重新获取或重新选择。软件只清理自己确认拥有的缓存文件，后台扫描或匹配进行时会避免与清理冲突。

页面还会复用已经读取和处理过的封面，接近可见区域时提前准备，并根据缓存容量逐步释放较旧内容。因此返回列表通常可以较快恢复海报，而不是每次都重新从网络下载。

### 标签和收藏针对本地来源

“已看”“待补完”等自定义标签属于你自己的整理信息，不同于软件的作品、系列、其他资源分类。

收藏夹可以跨资源库使用，一个来源也能加入多个收藏夹。删除收藏夹只删除集合关系，不删除视频。正常重扫保留标签和收藏；聚合作品上的这些操作会让你选择来源。

### 最近观看记录的是播放启动

点击或双击视频后，软件按原始文件记录找到完整路径，把路径交给你配置的播放器。成功启动播放器后，才记录对应来源的最近观看时间。

这个时间表示“你通过 M²Shelf 发起了播放”。软件没有读取播放器进度，因此它不能证明一集已看完，也不会记录暂停位置或提供续播进度。启动失败时不会生成一条成功观看记录。

文件定位也按原始记录找到路径，在 Windows 资源管理器中选中准确文件。中文、日文、空格和特殊符号会按字面路径传递。附件则通过 Windows 默认关联程序打开。

## 十一 搜索 排序 语言和返回页面

### 搜索读取本地目录册

侧栏搜索默认覆盖全部资源库，保留上次关键词，你也可以切换范围。目录里的搜索入口可以限定当前资源库。

本地搜索和筛选会利用显示名、真实目录名、官方多语言标题、官方别称、标签等信息；搜索页还可以找到已索引的视频文件名。未扫描的新文件暂时不会出现在这些结果中。

“本地搜索”与“手动搜索 Bangumi”是两个入口：前者找你已有索引中的资源，后者查询官方作品条目来建立绑定。

### 四种排序各有自己的时间含义

| 排序字段 | 读取什么 |
| --- | --- |
| 标题 | 当前语言下的显示标题。 |
| 加入时间 | 来源进入索引的时间；收藏夹里使用加入该收藏夹的时间。 |
| 更新时间 | 已索引的所属视频或附件的最后修改时间。 |
| 观看时间 | 通过软件成功启动播放后保存的最近时间。 |

给作品改名、换封面或重新绑定，不会把源文件“更新时间”变成今天。源文件变化要经过扫描写入索引后，排序才能反映它；切换排序本身不扫描媒体盘。

作品按所属内容计算时间，普通目录浏览则体现可见目录内容。聚合作品取各来源相关时间的最新值。没有时间信息的条目会排到后面。

### 语言只改变显示

已绑定作品优先显示当前界面语言的官方标题；缺少时依次尝试中文标题、官方主标题、数据库显示名和真实目录名。

切换中文、英文、日文或韩文不会改写文件名，也不会把作品重新绑定成另一条目。搜索可以利用多语言标题，不只依赖当前显示出来的名字。

### 返回时恢复浏览位置

打开新详情通常从顶部开始。返回、Alt+Left 等操作在有保存状态时恢复之前的滚动、筛选、排序和显示方式。侧栏各浏览入口也各自保留会话内状态。

全部资源、资源库浏览和收藏夹会分别持久保存排序偏好；窗口尺寸、主题、语言等设置也会在重启后恢复。浏览状态恢复时仍会读取当前索引，避免恢复成修改前的旧内容。

## 十二 隐藏 升级和软件更新

### 隐藏后还能恢复

忽略或隐藏一个目录，会把它和下级内容排除在可见浏览、作品归属及自动匹配之外。原文件和软件内的名称、绑定、封面、标签、收藏继续保留。

如果隐藏时详情页正打开，刷新后会回到资源库；旧详情和返回历史不能越过被隐藏的父目录继续读取内容。

恢复入口在 **设置 → 资源库管理 → 已隐藏条目**。恢复会重新自动分类，而不是恢复隐藏前曾经选过的人工类型。

如果父目录被隐藏，单独恢复子条目仍不能让它越过隐藏的父目录显示出来；父目录也需要恢复。如果子条目曾独立被隐藏，恢复父目录不会擅自取消子条目的隐藏。

### 数据库升级保留已有记录

新代码需要保存新的信息时，启动会按顺序升级本地数据库结构。当前规则修订新增逐库扫描健康记录，并根据已有索引重新计算自动分类和归属。

这个升级不强制立即全盘扫描。已有索引能判断的先调整，信息不足的等待正常扫描补充。人工分类、显示名、标签、收藏、绑定和封面会保留。

历史上某个 CD1 可能已经被单独错误绑定。软件会保留这种绑定并提示核对，不自动删除它，也不直接搬到父作品。这样你可以依据实际资源决定怎样纠正。

### 软件更新只在你明确操作后安装

“启动后自动检查更新”查询 M²Shelf 是否有新的稳定版本。发现新版本后，你可以查看说明、开始下载，再确认安装。

下载安装包时会检查来源、版本、文件完整性和签名。免安装版使用辅助程序替换软件文件，并为失败恢复准备备份。涉及恢复的提示会持续显示，直到你确认处理结果。

这是对软件程序的更新，与扫描动画目录、补全别称分别运行。它不会借机整理或搬动你的媒体资源。

## 十三 常见情况的处理顺序

### 新放入的视频还没有显示

先确认所在目录已经加入资源库、没有隐藏，扩展名也在视频列表中，再手动扫描。扫描完成后仍未显示时，查看资源库健康状态和错误摘要。

### 视频存在 却没有作品卡片

先按文件夹浏览确认它已被索引，再检查所属目录的分类。它可能位于“其他资源”混合目录，或缺少明确主体的补充目录；这些情况不会仅凭有视频就生成作品卡片。根据真实内容决定是否人工设为作品。

### 分类对了 名称却匹配错了

检查当前 Bangumi 条目是否是正确季度和形式，再手动改绑。改显示名可以帮助后续提供名称线索，但已经保存的错误绑定需要明确改绑或清除。

### CD1 和 CD2 还是两张卡片

检查外层名称是否可用，分卷名是否完整符合规则，是否混有普通作品分支，文件标题或季数是否冲突，以及子目录是否已有人工分类或单独绑定。规则有意保守，不会只看到 CD 字样就合并。

### 同一动画有两份资源 但未聚合

未绑定的文件夹来源不会仅凭同名跨目录合并。确认它们确实对应同一部作品后，分别绑定到同一个官方条目。视频文件来源还需注意是否在同一物理目录、季数等线索是否一致。

### 清除整组绑定后 卡片分开了

共同官方身份被移除后，软件按剩余本地证据重新分组。两个不同目录的文件夹来源分开，符合当前聚合规则。

### 硬盘离线 旧作品还在

已有目录册保留，所以仍能看到作品。文件播放和定位需要磁盘可访问；重新连接后扫描或重试即可。离线不会被当成整库文件全部删除。

### 封面失败 作品还能播放

封面、绑定和原始视频分别保存。检查网络后重试封面即可；如果绑定本身正确，不必为恢复封面重新搜索作品。

### 改了显示名 文件名没有变化

这是显示名功能的作用范围：更新软件内的名字，保留硬盘上的原名。

### 在资源管理器中移动或改名后 原来的整理信息怎样处理

目前索引以路径识别来源。软件外部改变路径后，扫描可能把它识别为新来源，并清理成功扫描范围内已经消失的旧来源。

新路径不保证自动继承旧路径的绑定、标签和收藏。M²Shelf 目前没有根据文件内容指纹追踪外部移动的机制；在软件内只改显示名则会保留原路径身份。

### 作品很多 别称没有一次补全

历史补全受每次运行 32 个不同条目的预算限制，并会在后续启动续跑。它也只补全官方提供的别称，不会自动创造官方没有收录的译名。
